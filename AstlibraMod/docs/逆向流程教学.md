# ASTLIBRA 随时存档 Mod —— 逆向流程教学（新手向）

面向逆向小白，复盘这次从"什么都不知道"到"跑通 Mod"的全过程。
所有脚本在 `analysis/`，源码在 `AstlibraQuickSave/`。

---

## 0. 先建立正确的心态

逆向不是"一眼看穿"，而是**把一个大问题拆成一串能验证的小问题**：

```
我要的目标
  └─ 游戏怎么存盘？        ← 小问题 1
       └─ 存盘函数在哪？     ← 小问题 2
            └─ 谁调用它？    ← 小问题 3
                 └─ 什么条件才允许调用？ ← 小问题 4
```

每一步都**必须先有证据**（字符串、代码片段、运行日志），再下结论。
猜错了没关系，但要能被下一步的观测推翻。这次我就猜错过两次（见第 9 节）。

三条腿一起走：

| 手段 | 看什么 | 工具 |
|---|---|---|
| **静态分析** | 文件里有什么 | Python + pefile + capstone |
| **动态调试** | 运行时发生什么 | x64dbg / 自写注入 DLL |
| **目标验证** | 游戏里真的生效吗 | 截图 + 按键驱动 + 日志 |

## 1. 侦察：这是个什么程序？

任何游戏逆向第一步都是**读 PE 头**。

```python
import pefile
pe = pefile.PE("ASTLIBRA.exe")
print(hex(pe.OPTIONAL_HEADER.ImageBase))   # 0x140000000  镜像基址
print(hex(pe.OPTIONAL_HEADER.AddressOfEntryPoint))  # 入口点 RVA
for s in pe.sections:                       # 各段
    print(s.Name, hex(s.VirtualAddress), hex(s.Misc_VirtualSize))
```

ASTLIBRA 的结果：`.text` 从 RVA `0x1000` 开始。**所有后面的地址我都用 RVA（相对虚拟地址）表示**，
因为运行时基址每次都不一样（见第 6 节）。

然后看**导入表**（它调用了哪些系统函数）：

```
KERNEL32.dll (87): CreateFileW, WriteFile, ReadFile ...
USER32.dll (8), SHELL32, WINTRUST, steam_api64
```

> 结论 1：没有 d3d9/d3d11/dxgi 的静态导入 → 图形 API 是运行时动态加载的。

**最关键的突破口是字符串**：二进制里几乎只有字符串是"人类可读"的。

```python
for off, s in find_ascii(段数据, 最短长度=4):
    if 关键字 in s: print(hex(rva), s)
```

一搜就出来了宝库：

```
...\Common\Source\Common_SaveLoad.cpp        ← 存档/读档的源码文件名！
...\Develop\DxLib\DxLibSource\DxWindow.cpp   ← 引擎是 DxLib（日本常用游戏库）
ALBR_SAV                                     ← 存档文件魔数
%s\ASTLIBRA\SAVE\SAVE_%04d.DAT               ← 存档路径格式串
```

> 结论 2：**编译时没去掉源码路径**。这是巨大的顺风车——直接告诉我们引擎（DxLib）和模块职责。

## 2. 找锚点：从字符串到代码

有了字符串，问题变成：**哪段代码引用了这个字符串？** 这叫 **交叉引用（xref）**。

### 为什么不能直接搜字符串的"绝对地址"

x64 程序访问数据用的是 **RIP 相对寻址**：

```asm
lea rcx, [rip + 0x8b065d]     ; rcx = 下一条指令地址 + 0x8b065d
```

`0x8b065d` 是**相对偏移**，不是绝对地址。要在文件里找"谁引用了 RVA 0x8cd248"，
就得反汇编，算出每条指令的目标，再比对。

### 做法一：capstone 线性扫描

```python
MD = capstone.Cs(capstone.CS_ARCH_X86, capstone.CS_MODE_64)
MD.detail = True
for insn in MD.disasm(代码, 起始RVA):
    for op in insn.operands:
        if op.type == X86_OP_MEM and op.mem.base == X86_REG_RIP:
            目标 = insn.address + insn.size + op.mem.disp
```

### ⚠️ 大坑：线性扫描会"失步"

代码段里混着跳转表等**数据**。从某个错误位置开始"解码"，垃圾字节也能被解码成合法指令，
于是**整段对齐全错**，真实的指令被跳过——我就因此漏掉了关键的调用者。

### 做法二（可靠）：字节级穷举

RIP 相对寻址的指令，其 ModRM 字节满足 `(modrm & 0xC7) == 0x05`，后面紧跟 4 字节 disp32。
于是可以穷举所有可能：

```python
for P in range(len(code)):
    for L in range(5, 12):              # 指令长度
        m = P + L - 5                    # ModRM 的位置
        if (code[m] & 0xC7) != 0x05: continue
        disp = int32(code[m+1:m+5])
        target = (va + P) + L + disp     # ← 目标 RVA
        if target == 想找的地址: 记录(P)
```

见 `analysis/refs.py`。会有少量重复命中，按"相邻地址合并成一簇"去重即可。

## 3. 划分函数边界：.pdata

不知道函数从哪开始、到哪结束，就没法看懂代码。x64 的 **`.pdata` 段**（异常处理表）
恰好存了每个函数的 `(起始RVA, 结束RVA, unwind信息)`：

```python
for i in range(0, len(raw)-11, 12):
    begin, end, unwind = struct.unpack_from("<III", raw, i)
```

见 `analysis/funcs.py`。有了它就能回答"0x1c980 属于哪个函数"。
本例共 9960 个函数。

---

## 4. 找调用者：暴力搜 `E8/E9`

`call` 的机器码是 `E8 <rel32>`，`jmp` 是 `E9 <rel32>`，目标是 `指令地址 + 5 + rel32`。
直接扫字节比反汇编可靠（不受失步影响）：

```python
for i in range(len(code)-5):
    if code[i] in (0xE8, 0xE9):
        rel = int32(code[i+1:i+5])
        目标 = (va + i) + 5 + rel
        if 目标 == 要找的函数: 记录(va + i)
```

这一步找出了存档函数的关键调用链。

## 5. 看懂代码：整体结构 > 逐条指令

看不懂一大坨汇编时，**先找它的"骨架"**：跳转表（switch）。

这次发现了这样一段（`analysis/dump.py` 打印）：

```asm
cmp byte ptr [rip + ...], 1     ; 比较某个全局字节
jne ...
call 0x140416010
call 0x140020830                ; ← trace 显示存档时就在这条链上
cmp byte ptr [rip + ...], 2
jne ...
call 0x1403bf050
...
```

**这是一张 0~16 的分发表**：全局字节 `.data 0x1BABB43` 就是**当前界面 ID**
（0=场景，1=存档界面，2=读档界面，…）。主循环每帧读它，调用对应界面的处理函数。

> 结论 3：把"打开存档界面"简化成了"把这个字节改成 1"。

## 6. 动态：把文件地址对到运行时地址

### RVA 与 ASLR

程序每次启动，基址都不同（ASLR）。所以：

```
运行时绝对地址 = 本次基址 + 文件里的 RVA
本次基址 = 绝对地址 - RVA        ← 反推
```

### 一个我自己踩的坑（值得记住）

旧版 trace 日志里写着 `frame0=0x140699571450247`——**带 `0x` 前缀但其实是十进制**。
原因是 C++ 代码这么写的：

```cpp
line += " frame" + std::to_string(i) + "=0x" + std::to_string(addr);
//                       ^^^^^^ 十进制数字，却被硬拼了个 "0x"
```

我照着它算 RVA，整体差了 `0x10000`，一度以为函数找不到调用者。
**教训：看到日志数字，先确认它到底是几进制。**

### 怎么验证基址算对了

不是靠猜，而是**拿一个已知事实去对**：

我提前找到了 `WriteFile` 在导入表里的位置，并搜出了谁调用它——`0x84F181 call [WriteFile]`，
那么返回地址必然是 `0x84F187`。而这个值和 trace 里 WriteFile 的 caller 对上了 → **基址确认无误**。

> 这就是"用静态分析验证动态数据"。

## 7. 找到真正的存档函数

顺着调用链（trace）逐层看：

```
主循环 → 分发表 → 存档界面处理函数 → SaveCommit(0x1C270) → 写文件
```

在 `SaveCommit`（RVA 0x1C270）里看到：

```asm
movabs rax, 0x5641535F52424C41   ; = "ALBR_SAV"（小端）
mov [0x1BED740], rax             ; 写入存档头
...
imul esi, dword [0x1BDF4A0], 0x64 ; 槽位 = 某个全局 * 100 + 参数
```

到这里，"存档是怎么完成的"就完全清楚了。

## 8. 实现：改状态，而不是改文件

**核心设计决定**：不要自己写存档文件（容易写坏），而是**触发游戏自己的存档流程**。

做法：写一个 DLL，注入游戏后在热键时**把那一个界面字节改成 1**，
等价于"你在存档点按了交互键"。游戏自己会完成剩下的所有事。

```cpp
WriteByte(base, kFlagAOffset, 0);          // 复现游戏开菜单时写的那几个字节
WriteByte(base, kFlagBOffset, 0);
WriteByte(base, kScreenIdOffset, 1);       // 界面 = 存档
WriteByte(base, kMenuOpenFlagOffset, 1);
```

再加**版本校验**（比对 RVA 0x4533FF 处的原始字节），保证只在 V1.5.0 上生效：

```cpp
const unsigned char sig[] = {0x80,0x3D,0x3D,0x87,0x75,0x01,0x01};
memcmp(base + 0x4533FF, sig, 7) == 0;      // 不符就不装
```

## 9. 验证闭环：日志 + 截图 + 按键驱动

光"觉得对"不算数。我的验证方式：

1. **日志**：DLL 每次动作写 `AstlibraQuickSave.log`，并顺带记录 `CreateFileW/WriteFile`
   是否真的写了 `SAVE_*.DAT`（这就是"存档成功"的铁证）。
2. **截图**：用 `um win shot` 抓游戏窗口，肉眼确认界面。
3. **按键驱动**：用 `um win drive --proc ASTLIBRA "focus" "key 0x74"` **只对游戏窗口发键**，
   不污染其它程序。

一次成功的证据长这样：

```
F5 save: screen 0 -> 1
CreateFileW ...\SAVE_0202.DAT
WriteFile SAVE bytes=28672 ok=1
WriteFile SAVE bytes=1268  ok=1
```

## 10. 我踩过的坑（请务必看）

| # | 坑 | 症状 | 原因 | 教训 |
|---|---|---|---|---|
| 1 | 日志进制 | 地址差 0x10000 | `std::to_string` 输出十进制却拼了 `0x` | 看到数字先确认进制 |
| 2 | capstone 失步 | 找不到调用者 | 线性反汇编遇数据段跑偏 | 关键搜索用**字节级暴力**兜底 |
| 3 | 误判函数职责 | 以为某函数是"存档点判定" | 只看了局部、没看调用者 | 单个函数看不出身份，要看**调用者**和**数据流水** |
| 4 | **改坏游戏状态** | **ESC 暂停菜单消失** | 我多设了一个"读档界面=2"，而读档界面不是这么进的，游戏卡在那个状态 | **只改最少的状态**；每个写入都要有对策（能恢复） |

第 4 条代价最大：后来加了 **F8 应急恢复**（强制把界面拉回场景），并**只让 F5 在场景界面生效**。

## 11. 工具清单 & 练习建议

### 工具
- **Python + pefile + capstone**：静态分析主力（本次全靠它）
- **x64dbg**：动态调试（下断点、看寄存器、改内存）——本次环境没装，用自写 DLL 替代
- **Cheat Engine**：找数值（血量/金币）的入门利器
- **universal-modder（um）**：`um win shot / drive / backup`，专门给 agent 用的游戏自动化

### 给新手的练习路径
1. 先玩 **Cheat Engine 自带教程**（找血量→指针→改代码），这是最好的入门。
2. 拿一个**小游戏**，用 pefile 打印段和字符串，认出引擎。
3. 学 **x64dbg 基础**：F2 断点、F7/F8 单步、看 `[rax+0x10]` 这种结构体访问。
4. 练 **xref**：找一句你认识的提示文字，反查谁引用它。
5. 再回头读 `analysis/` 里的脚本——你会发现它们就是上面几招的组合。

### 本项目可直接复用的命令
```bash
cd analysis
python dump.py 0x1C270 0x200       # 反汇编一段
python funcs.py 0x1C270             # 这个地址属于哪个函数
python refs.py 0x8CD248             # 谁引用了这个地址（字节级，可靠）
python xref.py 0x8CD248             # 同上（capstone 版，快但可能失步）
```
